—Executive Summary

This document describes the Claude Code agent configuration for TravelMatch, a quiz-based travel destination recommender. The setup consists of one custom MCP server exposing the matching engine as a callable tool, the IDE's built-in diagnostics integration, and Claude Code's core file/search/terminal tools used to build and maintain the project. TravelMatch has no custom skills directory and no committed sub-agent scripts — both are noted explicitly below rather than omitted, since their absence is itself part of an accurate setup record.

1MCP Servers

1.1Custom MCP Server: TravelMatch

Server name: travelmatch  ·  Type: stdio  ·  Status: Active  ·  Configuration file: .mcp.json  ·  Implementation: mcp-server/index.js

Configuration details

{ "mcpServers": { "travelmatch": { "command": "node", "args": ["mcp-server/index.js"], "env": { "TRAVELMATCH_BACKEND_URL": "http://localhost:8000/api" } } } }

Primary functions

  • Exposes 1 MCP tool, get_travel_recommendations, that mirrors the web quiz's answer shape.
  • Bridges an MCP client (Claude Desktop/Code) to the PHP backend via a single HTTP fetch call.
  • Validates tool input against a Zod schema before the request is sent.
  • Passes the backend's JSON results array straight through as tool-result text; on a non-2xx response, returns the raw response body as an error result.

Technical implementation

  • Framework: Node.js (ESM) with @modelcontextprotocol/sdk ^1.30.0
  • Communication protocol: stdio (standard input/output)
  • HTTP client: native fetch
  • Input validation: Zod ^4.5.4 schema on the tool's inputSchema
  • Timeout/retry: none configured — a single fetch with no explicit timeout, no retry, no backoff

Backend integration

  • API base URL: configurable via TRAVELMATCH_BACKEND_URL
  • Default: http://localhost:8000/api (no separate production URL is configured in .mcp.json)
  • Protocol: REST over HTTP, calling POST {TRAVELMATCH_BACKEND_URL}/match

1.2Built-in MCP Server: IDE Integration

Server name: ide (namespaced tools: mcp__ide__executeCode, mcp__ide__getDiagnostics)  ·  Type: Built-in  ·  Status: Active when connected to a supporting IDE  ·  Configuration: Automatic

Primary functions

  • Reads language-server diagnostics (lint/type errors) for a file from the connected IDE.
  • Executes code in a connected Jupyter kernel, where one is attached.

Usage context

Not specific to TravelMatch's own code — a general Claude Code capability surfaced when an IDE extension is connected. Not currently exercised by this project since it has no Jupyter notebooks and no tsconfig-driven language server; ESLint is run via the terminal instead (§3.3).

3.3Tool Usage Patterns

Recommendation workflow (via MCP)

  1. An MCP client calls get_travel_recommendations with the traveler's answers.
  2. mcp-server/index.js POSTs them to {TRAVELMATCH_BACKEND_URL}/match.
  3. The backend runs the same scoring engine the web quiz uses (see the project's SRS, §9) and returns the top 3 matches.
  4. The tool returns the results array as text content to the calling assistant.

Code development workflow

  1. Search the codebase: Grep or Glob.
  2. Read relevant files: Read.
  3. Make edits: Edit or Write.
  4. Verify: Bash — cd backend && php vendor/bin/phpunit (29 tests) or cd frontend && npm run lint.
  5. Run it: php -S localhost:8000 -t backend backend/index.php and npm run dev.

4Sub-Agents

Status: Not Configured

TravelMatch has no committed sub-agent scripts (no equivalent of a project frontend_tester.py) and no Playwright or browser-automation dependency in either backend/composer.json or frontend/package.json. Frontend verification is manual: run npm run dev and walk the quiz in a browser (documented as the verification step in the project's SRS, §10.1). Claude Code's general-purpose Agent tool can spin up an ad hoc subagent for a one-off task, but that is a session-time capability, not a script checked into this repository.

5Architecture Overview

5.1Communication flow

MCP Client (Claude Desktop/Code) ↓ MCP Protocol (stdio) travelmatch MCP Server (Node.js) ↓ HTTP (fetch) PHP Backend — front controller (index.php) ↓ PDO / pgsql PostgreSQL Database

5.2Tool invocation flow

  1. MCP client invokes get_travel_recommendations with validated arguments.
  2. mcp-server/index.js issues one fetch POST to the backend's /match endpoint.
  3. The backend's front controller (index.php) routes the request to api/match.php, which runs handleMatchRequest() against the destination catalog.
  4. The response is returned unmodified as MCP tool-result content, or as an error result on a non-2xx status.

5.3Error handling

MCP server error handling:

  • Non-2xx backend response: the tool call resolves as isError: true with the HTTP status and the raw response body text, untruncated.
  • Network/connection failure: the unhandled fetch rejection propagates to the MCP client as a tool-call error; there is no project-level catch or retry around it.
  • Input validation: handled by Zod against the tool's schema before any request is sent.

Backend error handling (the same handlers the web UI hits):

  • 422 for a missing required field, naming the field.
  • 400 for an unparseable JSON body.
  • 405 for a non-POST/OPTIONS method.
  • Gemini and n8n failures degrade to a working fallback rather than surfacing as an error — see the SRS §3.2 and §3.3.
Known gap

The MCP server has no configured request/connection timeout and does not truncate error text before returning it, and there is no authentication between the MCP server and the backend API. These are accurate as of the current code, not proposed changes.

6Configuration Files

Claude Code project settings: .claude/settings.local.json enables the server for this project:

{ "enabledMcpjsonServers": ["travelmatch"] }

6.2Backend configuration

File: backend/.env, loaded by backend/src/Env.php (a minimal parser — no external dependency, no framework)

Settings:

  • DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD — PostgreSQL connection
  • GEMINI_API_KEY, GEMINI_MODEL — optional; enables AI-generated descriptions
  • N8N_WEBHOOK_URL — optional; enables "email me my results"

backend/.env is git-ignored; nothing in it is committed.

8Security Considerations

8.1MCP server security

  • No authentication: the MCP server calls the backend API with no auth token — anyone able to run the MCP server can reach whatever TRAVELMATCH_BACKEND_URL points at.
  • Environment variables: the backend URL is read from TRAVELMATCH_BACKEND_URL, not hard-coded.
  • Input validation: Zod validates every tool call's arguments against the declared enum/shape before a request is sent.
  • No error sanitization: unlike a truncate-then-forward pattern, a non-2xx backend response is returned to the MCP client as raw response text, untruncated.

8.2Backend & network security

  • SQL access: exclusively parameterized PDO statements (Destinations.php, Rag.php, MatchEndpoint.php) — no string-concatenated queries.
  • CORS: every endpoint sets Access-Control-Allow-Origin: * — open to any origin, appropriate for a public read-mostly quiz API, worth narrowing before handling anything sensitive.
  • Secrets: backend/.env is git-ignored; GEMINI_API_KEY and DB credentials never appear in source.
  • Timeout protection: backend-to-Gemini calls (15s) and backend-to-n8n calls (8s) both have explicit cURL timeouts; the MCP-server-to-backend call (§1.1) does not.
  • TLS verification: outbound cURL calls pin a bundled CA file (backend/cacert.pem) via CURLOPT_CAINFO rather than relying on system CA config.

9Troubleshooting

9.1Common issues

MCP server not responding

  • Confirm node mcp-server/index.js starts without error and Node dependencies are installed (npm install in mcp-server/).
  • Check TRAVELMATCH_BACKEND_URL in .mcp.json matches where the PHP backend is actually listening.
  • Confirm the backend is reachable — GET /api/health should return {"status":"ok"}.
  • Confirm .claude/settings.local.json lists travelmatch under enabledMcpjsonServers.

Tool call fails or hangs

  • Verify the backend is running (php -S localhost:8000 -t backend backend/index.php).
  • Since no timeout is configured on the MCP-to-backend call (§8.1), a stalled backend will hang the tool call rather than time out.
  • Validate tool arguments match the enums in §3.1 — Zod will reject anything else before a request is sent.

Match results look wrong or descriptions look templated

  • Templated (non-AI) descriptions are expected behavior, not a failure, whenever GEMINI_API_KEY is unset — see the project's SRS §3.2/NFR-1.
  • Check backend/.env for a valid GEMINI_API_KEY and, if set, that GEMINI_MODEL names a real model.

"Email me my results" returns 503

  • Expected when N8N_WEBHOOK_URL is unset in backend/.env — set it up per automation/README.md first.

Sub-agents / custom skills

This Claude Code agent setup provides:

  • 1 custom MCP server exposing TravelMatch's destination-matching engine as a single tool, get_travel_recommendations.
  • 1 built-in MCP integration (IDE diagnostics/code execution), largely unused by this specific project.
  • 0 sub-agents and 0 custom skills — the project ships no automated frontend testing script and no packaged skill directory; verification is manual (PHPUnit for the backend, a browser walkthrough for the frontend).
  • Core Claude Code tools for file operations, code search, and terminal access, used to build and test the codebase.
  • One shared engine reachable from both the web quiz and any MCP client, so a human using the browser and an AI assistant using the tool get identical recommendations for identical answers.

The configuration enables the agent to develop and modify TravelMatch's code directly, verify changes with the existing PHPUnit suite, and — through the MCP tool — request live destination recommendations without leaving the chat.
