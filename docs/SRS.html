1Introduction

1.1Purpose

TravelMatch turns a nine-question quiz into ranked destination recommendations. A traveler answers questions on interests, travel style, weather preference, budget, companions, and the vibe of their ideal getaway; the backend scores a destination catalog against those answers, ranks the top matches, and writes a short personalized blurb for each — grounded in curated facts about the destination and generated by a language model when one is configured, or a deterministic template when it isn't. This document specifies what the system does, how its parts fit together, and how each requirement is verified.

1.2Scope

The system is one product delivered as four coordinated pieces:

  • Frontend — a React (Vite) single-page quiz that collects answers and renders results.
  • Backend — a PHP API that validates requests, runs the scoring engine, retrieves and generates personalized descriptions, persists submissions, and forwards email requests.
  • Automation — an n8n workflow, triggered by the backend, that formats and sends the results email.
  • MCP server — a Model Context Protocol server that exposes the same matching engine as a callable tool for Claude Desktop/Code and other MCP clients, so an AI assistant can request recommendations directly.

Out of scope: user accounts and authentication, destination content management (the catalog is seeded directly in PostgreSQL), and payment or booking flows. TravelMatch recommends; it does not book.

2Overall Description

2.1Product perspective

TravelMatch is a self-contained web application, not a component of a larger system. The backend is a plain PHP API (no framework) served by PHP's built-in development server via a front controller; the frontend is a static React build that talks to it over HTTP. PostgreSQL is the single source of truth for the destination catalog, its knowledge base, and logged quiz submissions. Two integrations are optional and the product is fully functional without either: Google Gemini for AI-written descriptions, and an n8n webhook for emailing results.

2.2User classes

AI-assistant userMCP client (Claude Desktop/Code)Ask an assistant for travel recommendations without leaving their chat.

2.3Operating environment

  • Backend: PHP 8.2+, PDO pgsql driver, cURL (incl. curl_multi), served with php -S.
  • Database: PostgreSQL, reachable from the backend host.
  • Frontend: any modern evergreen browser; built and served by Vite.
  • MCP server: Node.js, run as a stdio subprocess by an MCP-compatible client.
  • Automation: an n8n instance (self-hosted or cloud) with SMTP credentials.

2.4Design and implementation constraints

  • No PHP framework and no ORM — routing is one regex front controller, data access is hand-written PDO with parameterized queries.
  • Business logic is framework-free by construction: Matcher.php, Rag.php, MatchEndpoint.php, and NotifyEndpoint.php depend on no superglobals, so they run identically under PHPUnit and under the live server.
  • Secrets (GEMINI_API_KEY, N8N_WEBHOOK_URL, DB credentials) live only in a git-ignored backend/.env, loaded by a minimal parser in Env.php.
  • Any feature that depends on an external service (Gemini, n8n) must degrade to a working default rather than fail the request.

3Functional Requirements

3.1Quiz & matching

IDRequirement
FR-1The frontend shall present nine quiz questions in sequence (duration, interests, weather, companions, style, budget level, budget amount, ideal getaway, season) and allow moving forward only once the current question is answered.
FR-2On quiz completion, the frontend shall submit all collected answers to POST /api/match and render the returned results, or an error message if the request fails.
FR-3The backend shall reject a match request that is missing any of interests, style, weather, budgetLevel, or companions with HTTP 422 and name the missing field.
FR-4The backend shall score every destination in the catalog against the submitted answers on six weighted criteria (interests, style, weather, budget, getaway vibe, companions) and return the top 3 by composite score.
FR-5Each returned match shall include the destination's name, country, match percentage (0–100), a description, best time to travel, an estimated budget range, and a recommended stay length.
FR-6The backend shall best-effort log every match submission (answers plus the top match) to quiz_submissions; a logging failure shall never affect the response returned to the user.

3.2Personalized descriptions (RAG)

IDRequirement
FR-7For each of the top matches, the backend shall retrieve knowledge chunks about that destination ranked by tag overlap with the traveler's interests and budget level.
FR-8When GEMINI_API_KEY is configured, the backend shall generate a 2-sentence, ≤35-word description per match, grounded in the retrieved chunks, issuing all requests for one submission concurrently.
FR-9The backend shall reject a Gemini response that is empty, exceeds 60 words, or contains a line break, and use the destination's template-built fallback description instead.
FR-10When GEMINI_API_KEY is not configured, or any Gemini call fails for any reason, the backend shall serve the template-built fallback description with no visible degradation to the user.

3.3Notification, health, and MCP

IDRequirement
FR-11The frontend shall offer to email the traveler their results; on submission it shall call POST /api/notify with the email address and the results array.
FR-12The backend shall reject a notify request with a missing or syntactically invalid email address, or a missing/empty results array, with HTTP 422.
FR-13When N8N_WEBHOOK_URL is not configured, the backend shall return HTTP 503 with an explanatory error rather than attempt delivery.
FR-14The backend shall forward a valid notify request to the configured n8n webhook and return HTTP 502 if the webhook is unreachable or responds with a non-2xx status.
FR-15The backend shall expose GET /api/health returning {"status":"ok"} for uptime checks.
FR-16The MCP server shall register a get_travel_recommendations tool with a schema mirroring the quiz's answer shape, call the backend's /api/match on invocation, and surface the backend's error body if the call fails.

4Non-Functional Requirements

IDCategoryRequirement
NFR-1ResilienceThe quiz, match, and results flow shall function correctly with no AI description provider and no email provider configured — both are optional add-ons layered over a working core.
NFR-2PerformancePer-destination Gemini calls for one submission shall be issued concurrently via curl_multi, not sequentially, so RAG latency is bounded by the slowest single call rather than their sum.
NFR-3SecurityAll SQL access shall use parameterized PDO statements; secrets shall never be committed (backend/.env is git-ignored); CORS headers on each endpoint shall be explicit rather than implicit.
NFR-4TestabilityRequest-handling logic shall accept its collaborators (data access, matching, webhook delivery) as injected callables, so behavior is verifiable under PHPUnit without a live database or network.
NFR-5PortabilityThe backend shall run under PHP's built-in server with zero required framework and a single external runtime dependency (PostgreSQL); no build step is required to run it.
NFR-6ConsistencyThe scoring engine shall be the single implementation of match logic reachable from both the web UI (via /api/match) and any MCP client, so a human and an AI assistant get identical recommendations for identical answers.
NFR-7Output safetyA generated description shall never be shown to the user unless it passes the clean-output check (single paragraph, ≤60 words, no line breaks) in extractGeminiText.

6Design Patterns

6.1Front Controller

backend/index.php is the single entry point PHP's built-in server routes every request through. It matches /api/{name} against a whitelist regex and requires the matching file under backend/api/, returning 404 for anything else. Endpoint scripts never need to reason about routing, only about their own request.

6.2Dependency Injection for testability

handleMatchRequest() and handleNotifyRequest() take their side-effecting collaborators — getDestinations, matchDestinations, logSubmission, sendNotifyWebhook — as parameters rather than calling them directly. Production endpoint scripts (api/match.php, api/notify.php) pass the real functions; tests pass fakes. This is why the entire request-handling contract (validation, status codes, error bodies) is unit-tested without a database connection or an outbound HTTP call.

6.3Repository-style data access

Destinations.php and Rag.php isolate every SQL statement behind a narrow, purpose-named function (getDestinations(), retrieveKnowledge()) that returns plain PHP arrays. Matcher.php never touches PDO — it consumes arrays shaped like the destinations table and has no idea PostgreSQL exists, which is what lets it be tested with hand-built fixture arrays.

6.4Strategy-weighted scoring

Six independent scoring functions (scoreInterests, scoreStyle, scoreWeather, scoreBudget, scoreGetaway, scoreCompanions) each score one facet of fit on a 0–10 scale using only the fields it needs. rankDestinations() combines them by fixed weight into one composite. Each strategy can be reasoned about, and tested, in isolation.

6.5Retrieval-Augmented Generation with graceful fallback

Rag.php separates retrieval (rank destination_knowledge rows by tag overlap with the traveler's interests) from generation (prompt Gemini using the retrieved facts). Generation is wrapped so that a missing API key, a network failure, a timeout, or an unclean response all resolve to the same outcome — the caller's own fallback description — via one code path in generateDescriptionsBatch(), functioning as a circuit breaker around the one component the system does not control.

6.6Adapter (MCP server)

mcp-server/index.js adapts the HTTP /api/match contract to the MCP tool-call contract: it declares a Zod schema matching the quiz's answer shape, translates a tool invocation into a fetch POST, and translates the JSON response (or an HTTP error) into MCP tool-result content. No matching logic is duplicated — the adapter only translates.

7External Interfaces

7.1POST /api/match

Runs the quiz answers through the scoring engine and returns the top 3 destinations.

// request body { "duration": "medium", "interests": ["food", "history"], "weather": "warm", "companions": "partner", "style": "balanced", "budgetLevel": "moderate", "budgetAmount": 1200, "getaway": "romantic_luxury", "season": "spring" }
// 200 response body { "results": [ { "name": "Lisbon", "country": "Portugal", "match": 87, "description": "…", "best_time": "April–June", "budget_estimate": "€800–1400", "recommended_stay": "4–7 days" } ] }

Only interests, style, weather, budgetLevel, and companions are required. 400 = invalid JSON; 422 = missing required field; 405 = non-POST/OPTIONS.

7.2POST /api/notify

// request body { "email": "traveler@example.com", "results": [ /* same shape as match results */ ] }

200 {"status":"sent"} on success · 422 missing/invalid email or results · 502 the n8n webhook was unreachable or non-2xx · 503 no N8N_WEBHOOK_URL configured.

7.3GET /api/health

200 { "status": "ok" }

7.4MCP tool — get_travel_recommendations

Registered by mcp-server/index.js; input schema mirrors §7.1's body (getaway, duration, and season optional). Calls the backend's /api/match and returns its results array as tool-result text, or an error result on a non-2xx backend response.

7.5Google Gemini — generateContent

Called from generateDescriptionsBatch() at https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent, authenticated via the x-goog-api-key header, model configurable through GEMINI_MODEL (default gemini-flash-lite-latest). One request per matched destination, issued concurrently, 15s timeout each.

7.6n8n webhook

sendNotifyWebhook() POSTs { email, results } as JSON to N8N_WEBHOOK_URL, 8s timeout. The imported workflow (automation/n8n-workflow.json) is Webhook → Format Email (Code node) → Send Email: it reads $json.body.email / $json.body.results, builds an HTML table of the results, and sends it over SMTP.

8Testing Strategy

The backend has 29 PHPUnit tests (65 assertions), all currently passing, split across the modules that hold behavior worth verifying independently of a live database, network, or browser.

SuiteTestsCovers
MatcherTest12Every scoring function (interests, style, weather, budget, getaway, companions), formatBestTime, buildDescription, and rankDestinations — best match first, limit respected, score bounded to 0–100.
MatchEndpointTest7OPTIONS short-circuits with no side effects; non-POST rejected; invalid JSON rejected; missing required field named in the error; injected dependencies are called with the right arguments; the top match (or null) is what gets logged.
NotifyEndpointTest9OPTIONS/non-POST handling; missing email or results; invalid email format; no webhook configured (503); webhook payload passthrough; success, failed cURL, and non-2xx webhook responses (502).
HealthEndpointTest1healthCheck() returns the documented shape.

8.1How it's testable without infrastructure

This suite runs with no PostgreSQL instance, no Gemini key, and no network access — it exercises exactly the pattern in §6.2. tests/bootstrap.php requires the source files directly (there is no autoloader, matching the project's no-framework stance), and every handler test substitutes a closure for each injected collaborator, asserting both on the returned {status, body} and, where relevant, on what the closures were called with.

8.2Deliberately untested by design

  • Gemini integration (generateDescriptionsBatch, extractGeminiText) — exercises live cURL and a real API key; verified manually against the fallback behavior in §3.2 rather than mocked.
  • Database access (getDb(), getDestinations(), retrieveKnowledge(), logSubmission()'s SQL) — thin PDO wrappers; the logic worth testing sits above them and already is.
  • Frontend — no automated test suite; verified by running the quiz end-to-end in a browser (see §10).

8.3Running the suite

cd backend composer install php vendor/bin/phpunit # 29 tests, 65 assertions, OK

9System Architecture

Five layers, each depending only on the one below it. Business logic (Matcher.php, Rag.php) has no dependency on the web layer above it or the database layer below it — it is pure functions over arrays, which is what makes §6.2 and §8 possible.

9.1Scoring weights

rankDestinations() combines six 0–10 sub-scores into one composite via fixed weights before scaling to a 0–100 match percentage.

Interests0.35
Style0.15
Weather0.15
Budget0.15
Getaway vibe0.15
Companions0.05
Total1.00
match% = round( clamp( Σ (score_i / 10) × weight_i , 0, 1 ) × 100 )

10Implementation Plan

The build proceeded bottom-up: data shape and scoring first (fully testable with no infrastructure), then the HTTP surface, then the two optional integrations, then the UI and the MCP adapter, then the test suite hardening each layer.

10.1Verifying a change end-to-end

  1. Run php vendor/bin/phpunit from backend/ — all 29 tests must pass.
  2. Start the backend (php -S localhost:8000 -t backend backend/index.php) and the frontend (npm run dev in frontend/).
  3. Walk the quiz in a browser end-to-end; confirm results render with a match %, description, best time, budget, and stay length.
  4. Confirm the app still works with GEMINI_API_KEY and N8N_WEBHOOK_URL unset (NFR-1) — descriptions fall back to templates, and "email me my results" returns a clear 503 rather than hanging or crashing.

11Conclusion

TravelMatch demonstrates a focused, well-scoped recommendation system that combines a weighted multi-criteria scoring engine with retrieval-augmented, AI-generated personalization, while remaining fully functional if the AI or email integrations are unavailable. Its layered PHP backend, dependency-injected request handlers, and repository-style data access keep the core matching logic simple, testable, and independent of any single external service. By additionally exposing the matching engine through an MCP tool, TravelMatch shows how the same core business logic can serve both a traditional web UI and AI-assistant clients. This SRS has documented the system's scope, functional and non-functional requirements, UML models, design patterns, interfaces, testing strategy, architecture, and implementation plan as a complete reference for the project.
